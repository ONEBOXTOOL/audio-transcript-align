# 校对页 UI · 三个方向

这页是 `preview.html` 的 UI 方案对比，不是最终实现。三份原型都用**真实 gold 数据**（`data/gold/episode.json`，76 句 / 6:28.82 / 平均对齐 0.993）渲染，桌面 1440×900、手机 390×844。

- 总览：`compare.png`
- 原型：`option-a.html` / `option-b.html` / `option-c.html`（浏览器直接打开，可播放、可改边界）
- 截图：`shot-{a,b,c}-{1440,390}.png`
- 数据：`data.js`（句子 + ASR 词 + 两档波形峰值，峰值由 `av` 解码后算 RMS）

> 原型只演示交互与信息架构：导出按钮是真的，刷新会丢改动；生产版需要补持久化与数据契约（见文末）。

## 先看结论

**推荐 01 波形精修台**。这个工具的核心工作是「判断边界对不对」，波形是唯一能一眼看出切首词、切尾词、句间静音的视图；02 的队列适合当它的一个「低置信度模式」，03 更适合作为交付给听众的阅读页。

如果目标变成「每天批量过 10 期，每期只扫一遍」，则选 02；如果目标是把对齐结果直接当听力页发出去，选 03。

## 01 波形精修台（Waveform workbench）

**信息架构**：顶部播放条 + 全片波形；左栏句子列表；右栏当前句编辑器。

**主流程**：点波形或列表选句 → 听 → 拖绿色边缘 / ±0.1 / 重打点 → 看词级时间戳确认 → 下一句。

**关键交互**

- 全片波形按说话人着色，当前句高亮，静音缝隙直接可见；支持 1× / 2× / 4× 缩放。
- 拖动选中句两侧手柄改 `start/end`，键盘 `[ ] ; '` 微调。
- 下方显示落在本句区间内的 ASR 词及时间，方便判断「首词是不是被切了」。
- 搜索、低置信度 / 已改过滤；列表与波形联动。

**需要的数据**

- `peaks`：生成时用 `av` 解码，10ms RMS 聚合到 2400 点（全片）和 12000 点（放大/单句）。76 句约 160KB JSON，可内联。
- 词级时间戳：`asr_words.json` 已有；原型按时间区间过滤，生产版最好在 `align()` 里记录 token→word 索引，避免边界附近误配。

**代价**：前端最重。波形绘制、缩放、拖拽、命中测试都要自己写；没有框架可借。移动端全片波形只有几像素宽，精修仍应回到桌面。

## 02 审阅队列（Review queue）

**信息架构**：左栏队列 + 中间单句卡片；没有全局波形。

**主流程**：听当前句 → 判断准确 / 改边界 / 跳过 → 自动下一句。顶部是进度，左侧是 76 句的状态清单。

**关键交互**

- 单句波形（只画这一句的 5 秒），局部细节比全片波形清楚。
- 大按钮「准确，下一句」+ `Enter`；`S` 跳过；`J/K` 前后句；`R` 重播。
- 队列状态：已过 / 当前 / 未过；支持「未过」「已改」过滤。
- 通过后可自动跳到下一个未过项，适合低置信度批量清理。

**需要的数据**：现有 `episode.json` 足够；通过状态存 `localStorage`，导出时只写时间轴。

**代价**：没有全局视角，看不出「整期哪里空了一大段」；精修能力弱于 01。适合当 01 的一个模式，而不是独立产品。

## 03 沉浸精读稿（Reader）

**信息架构**：单栏阅读页 + 底部悬浮播放器；没有列表、没有波形。

**主流程**：按说话人分段阅读 → 播放时当前句高亮跟随 → 需要时打开「编辑」在底部调边界。

**关键交互**

- 句子还原成对话段落，说话人与时间在左侧 gutter；当前句浅绿高亮。
- 点击任意句从该句播放；播放器有进度、变速、前后句、循环。
- 「编辑」展开底部时间输入与 ±0.1、重打点；改动标 `edited`。
- 支持 `#s16` 这样的 hash 直接定位到某句。

**需要的数据**：无新增。适合直接作为 `preview.html` 的另一种输出模式，甚至作为听力页交付。

**代价**：边界编辑弱；76 句长稿靠滚动定位，找特定句不如 01/02；不适合当唯一校对工具。

## 横向对比

| | 01 波形精修台 | 02 审阅队列 | 03 沉浸精读稿 |
|---|---|---|---|
| 核心动作 | 看边界、拖边界 | 逐句判断 | 读、跟读 |
| 全局视角 | 强 | 弱 | 中（靠滚动） |
| 精修效率 | 高 | 中 | 低 |
| 批量过稿 | 中 | 高 | 低 |
| 移动端 | 可用，但波形太密 | **最好** | **最好** |
| 新增数据 | peaks（+ 词级索引更佳） | 无 | 无 |
| 前端成本 | 3–4 天 | 1.5–2 天 | 约 1 天 |
| 适合当 | 主校对台 | 主校对台的低置信模式 | 交付页 / 阅读模式 |

## 架构落点

三种方案都应该保持现在的交付形态：**单个 `preview.html`、`file://` 可开、无后端、音频不外嵌**。

但源码不建议继续放在 Python 字符串里（现在是 `PREVIEW_TEMPLATE`，约 330 行）。建议：

```text
preview/
  template.html     # 结构 + 占位符
  app.css
  app.js
  peaks.py          # av 解码 → 峰值
audio_align.py      # render_preview() 读取并内联上面三个文件
```

产物仍是单文件，源码可读、可 lint、可复用；不需要引入 React/Vite，也不需要本地服务。只有出现「自动保存 / 多人协作 / 大文件流式加载」时才考虑本地 server。

### 状态与持久化

- 现在：所有改动只在内存，刷新即丢；导出是唯一落盘路径。
- 01/02 建议：`localStorage` 按 `title + duration` 存草稿，打开时提示「恢复上次修改」；导出仍以 JSON 为准。
- 更进一步：Chrome 的 File System Access API 可以直接覆盖写回 `episode.json`，但要处理权限与兼容性，不建议第一版做。

### 生产化前置（与 UI 无关，但会影响契约）

1. **duration 收口**：`--asr-json` 或时长探测偏小时，末句 `end < start`；JSON 里的 `duration` 也要用校正后的值。
2. **edited / needs_review**：导出目前会多写 `edited`，但 README 的 schema 没有；手改后 `needs_review` 不重算，低置信度筛选会失真。
3. **跨盘音频 URL**：`file:///` 分支没做 `quote`，路径含 `#`/`?` 时会加载失败。
